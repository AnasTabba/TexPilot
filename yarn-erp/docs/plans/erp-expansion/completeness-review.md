## 0. How to read the matrix

Status legend (one value per row; strongest fleet-wide caveat first):

- **live·tested** — implemented in the released baseline and covered by the automated suite (unit, API, or a browser spec recorded in `docs/releases/2026-10-28-procurement.md`; browser suites were not re-run here).
- **live·manual** — implemented in the released baseline, verified by code reading, no automated coverage in this repo.
- **branch-only** — written inside a wave worktree, uncommitted and untested; may be replaced by its owner at any time.
- **missing** — no code and no in-plan ownership yet.
- **decision** — deliberately deferred until root/user chooses the scope (must not skip user sign-off).
- **setup-blocked** — code path exists but needs a real-world input (credential, provider contract, e-mail domain) that no worker may supply.

"Owner" = the single worker/role that must move the row; "shipped" rows need no further owner except where noted. Every acceptance check is a command/fixture/expression of behavior, not prose intent.

## 1. Original user requirements reviewed against

1. A genuinely deep **complete factory app** (studio floor: machines, shifts, batches, stock truth).
2. **Proper RFQ/procurement**: directory → verified suppliers → RFQs → bids → award → PO → shipment → receipt.
3. **Seamless supplier workflows** (supplier portal parity: identity, bid room, dispatch docs, tracking).
4. **Container/B-L tracking** wired to real paid lookups with honest spend control.
5. **Sales side**: buyers, quotes, orders, invoices, payments, reminders.
6. **New operational chat**.
Plus standing constraints: workspace isolation, auditability, reversible unsafe actions, mobile-first Urdu.

## 6. Product recommendations (role queues, one timeline, contextual chat)

1. **Role action queues, not more dashboards.** Each permission family gets one Home card with a real count or hidden entirely (F8 in finish-review): `procure/receive` → POs awaiting receipt; `qc` → lots uninspected/hold; `suppliers` → pending reviews; `sales (wave-B)` → quotes awaiting approve / receivables open; `tracking (wave-D)` → targets in `needs_reconcile`/`renewal_paused`. No fabricated metrics: counts come from the same list APIs, not bespoke rollups.
2. **One linked order timeline** (F7): one endpoint + one component reused by supplier PO, sales order and later chat anchor. Each node deep-links (`YF:<id>`), receipts already know their lots (`IncomingStock.tsx:20`), so the PO→batch→dispatch→invoice chain becomes traversable without re-implementing per-screen.
3. **Contextual chat** (chat worker + UI worker): the thread opens *inside* the record the user is looking at (PO, RFQ, batch, shipment) and the record’s timeline shows "message sent" nodes; no org-wide notice duplicator, no presence indicators, no analytics virality. Blocks: retention visible ("kept while the workspace is kept"), actor attribution through the same `actor` checks, suspension removes a member instantly.
4. **Do not build:** a second invoice screen, parallel supplier/contact book, custom notification center, or “productivity score” cards — each duplicates an existing flow and would drift out of sync.
