## P1 — Drift suspension has no executable monitoring owner or acceptance contract

**Evidence:** Design line 161 requires per-domain monitoring and drift alerts that suspend automation. Plan line 218 maps this to T09/T11/T12, but T09 owns dataset splits, T11 owns initial release statistics, and T12 (lines 178–188) creates a benchmark, parity/fault tests and a runbook; none names a monitoring implementation, evaluation cadence, baseline/window/minimum support, missing-audit handling or alert-to-suspension interface. Existing `yarnflow/server/cloudflare.mjs:25–26` schedules only purchasing/reminders/credit/tracking; `yarnflow/wrangler.jsonc:19–20` enables observability and hourly cron, which does not implement this requirement. `scanner/services/api/main.py:58–68` supplies liveness/basic model readiness, not drift detection.

**Impact:** All listed task tests could pass while a valid, unexpired release keeps accepting samples after coverage/OOD or delayed error evidence shifts. A manual revoke drill proves the switch works, not that the promised drift trigger reaches it.

**Correction:** Give T12 an explicit owning monitoring implementation, using existing Worker scheduling/storage where suitable. Pin a versioned, authority-approved monitoring protocol per released domain: counters and denominators, audit eligibility/probabilities, window/cadence/support, incident triggers and stale/missing telemetry behavior; bind the protocol and operational drill evidence to automation eligibility. Do not invent statistical thresholds in implementation. Define detection latency separately from the existing immediate commit-time suspension check.

**Test assertion:** Feed a fixed approved protocol normal, shifted, sparse and missing-audit streams under an injected clock; assert exact domain-scoped suspension and an auditable incident, unaffected domains unchanged, no automatic finalization after suspension, and restart/repeated scheduler invocation does not lose or duplicate the incident. Missing required monitoring proof prevents automatic promotion. G2/G7 own statistical authority; G8 owns operational signoff.

## P1 — Required recall notices are absent from the persistence/API/task contract

**Evidence:** Design line 161 promises immutable old decisions plus recall notices to reviewers for affected evidence. The authoritative proposed table list at line 145 has decision events but no defined recall event payload, affected-set query, recipient/acknowledgment semantics or retry state. Plan line 40 exposes release suspension and sample history, but T05/T12 assertions test revocation/immutability without asserting any historical recall or notice delivery. Existing `yarnflow/server/notify.mjs:5,10–18,20–39` provides recipient notifications and read status; its event list has no incoming-QC release recall, and no planned task extends this owner. Existing notification listing is limited to the latest 100 records (`notify.mjs:25`), so a notification alone is not a complete authoritative affected-decision view.

**Impact:** New decisions can fail closed while previously accepted affected samples remain apparently trustworthy to reviewers; immutable history alone does not communicate withdrawal.

**Correction:** Define append-only release/domain incident and affected-decision recall semantics in T01/T02 and implement them through T05/T12. Reuse decision events plus existing notifications where appropriate; provide a tenant-scoped authoritative recall view independent of the notification page limit. Bind affected decisions by release/artifact/domain and incident cutoff; preserve original status and distinguish historical ACCEPT from current recalled validity. Make notification retries idempotent and observable.

**Test assertion:** Suspend a release with more than 100 affected historical decisions, including two tenants and an in-flight request; every affected decision is discoverable as recalled, no unrelated decision is recalled, the in-flight stale decision does not commit, each intended reviewer receives at most one notice per incident, and delivery failure/restart retries without mutating original decisions. Authority specifies incident scope/recipients under G8; no stock/claim/dispatch effects occur.

## P1 — Restore/replay can resurrect consent-deleted evidence; retention and immutability are not reconciled

**Evidence:** Design line 139 requires deletion/tombstones, training exclusion and backup expiry; line 145 says immutable evidence and orphan GC must never delete live references; line 147 specifies restore/reconciliation but does not say consent tombstones override restored content. Plan T02 line 64 and T12 line 184 test matching blobs and later-write reconciliation, without a deletion-before-restore assertion or a durable deletion authority outside the restored snapshot. T09 line 148 requires a signed retention gate but assigns no deletion worker/storage lifecycle implementation. Actual storage primitives are unconditional `put/get/delete` (`yarnflow/server/d1-bucket.mjs:9–23`, local files in `yarnflow/scripts/dev-server.mjs:48–53`); local SQLite uses WAL (`dev-server.mjs:20`), and deployment D1 configuration has no separate BUCKET (`wrangler.jsonc:16–18`). No inspected primitive enforces tombstones. Legacy scanner storage writes photos then rows (`scanner/services/api/store.py:44–63`) and Modal retains that store on a separate volume (`scanner/deployment/modal_scanner.py:14,50,73`).

**Impact:** Restoring a consistent old snapshot can still restore withdrawn originals or eligible training records. Conversely, enforcing “never delete live references” literally can prevent an authorized retention purge. Backup consistency alone does not settle either case.

**Correction:** Before collection under G4, specify metadata-versus-payload retention, legal hold precedence and a tombstoned/unavailable evidence state that preserves permitted audit lineage without serving deleted bytes. Assign implementation/tests to T02/T09/T12. Define a monotonic deletion ledger or equivalent recovery input that survives an older DB restore; replay it before restored service/training access opens. Inventory every in-scope copy, explicitly including any legacy scanner/Modal diagnostic copy if v2 ever writes there (otherwise assert v2 never does). Parameterize the restore drill for D1-contained blobs and local WAL/separate files; destructive purge remains separately authorized by the signed retention policy.

**Test assertion:** Capture and snapshot, then withdraw/delete, then restore the old snapshot to an isolated target and reconcile; the withdrawn bytes remain unavailable, derived dataset entries remain excluded, allowed audit hashes retain a tombstone, retries are safe, held evidence follows the signed policy, and live nonexpired evidence is retained. Verify backup expiration and no v2 originals in the legacy store. G4 determines retention/withdrawal rules; G8 approves recovery proof, with no collection until both applicable gates pass.

## Final disposition

The drafts correctly identify external factory, statistics, privacy and recovery authority gates; their absence is not itself a defect. The gaps above are missing executable ownership and test contracts for behavior the design already promises. Close them before automation/field collection as applicable; retain review-only fallback and do not infer release readiness from synthetic tests or this review. No product files changed, no installs/deployments/GPU jobs/purchases performed; verification was source inspection only.
